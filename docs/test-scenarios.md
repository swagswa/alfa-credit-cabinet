# Сценарии проверки

Стенд: `docker compose up -d --build --wait`, фронт http://localhost:8000, Temporal UI http://localhost:8233 (namespace `default`, id процесса равен id заявки из карточки). Учётки и ИНН демо-компаний в [README](../README.md#тестовые-учётки), пароль у всех `demo12345`. Те же шаги запросами: коллекция Bruno в `collections/credit-cabinet/`.

Два кабинета сразу открывайте в разных браузерах или в обычном и приватном окне: cookie сессии общий на браузер.

Сценарии 1-17 проходят на текущем main. Сценарии из таблицы в конце зависят от скоринга, решения, подписания и ленты, которые ещё не встроены в процесс: на сервере `decision`, `accept`, `sign`, `signing-code` и `feed` пока отвечают 501, а заявка, прошедшая все проверки, остаётся в `checking`.

## Работает

### 1. Чистый старт

На свежем клоне `docker compose up -d --build --wait`. Ждём: команда выходит без ошибок, `docker compose ps` показывает `healthy` у `db`, `redis`, `api`, `mocks`; `curl localhost:8080/api/health` отвечает 200 и `ok` по `db`, `temporal`, `redis`. Демо-учётки входят без ручных шагов.

### 2. Перезапуск

Подать любую заявку, затем `docker compose down` (без `-v`) и снова `up -d --wait`. Ждём: заявка на месте с тем же статусом и журналом, сессия жива (Redis с AOF), учётки и компании не задублированы.

### 3. Вход, выход, лимит

`coffee` с неверным паролем и несуществующий логин дают одинаковое «неверный логин или пароль» (401). Одиннадцатая попытка за минуту с одного адреса: 429. Войти `coffee` в двух вкладках, выйти в одной: вторая на следующем запросе получает 401, сессия удалена на сервере.

### 4. Черновик и подача

Учётка `coffee`. Подобрать продукт, оборотный кредит 2,5 млн на 24 месяца, отметить согласия на БКИ и обработку данных, подать. Ждём: статус `submitted`, затем `checking` без перезагрузки страницы. В Temporal UI процесс `ApplicationWorkflow` с id заявки: четыре `FetchSource` (egrul, fns, bki, internal) запущены разом, все завершены. У сотрудника `manager` в карточке блок проверок с ответами всех источников. Дальше заявка остаётся в `checking`, процесс завершён: решения пока нет.

### 5. Повтор подачи

API: два `POST /api/applications` с одним `Idempotency-Key` и одним телом дают одну и ту же заявку. Тот же ключ с другим телом: 409 `idempotency_conflict`. Повторный `submit` поданной заявки отвечает 200 с карточкой, в Temporal UI по-прежнему один процесс с этим id.

### 6. Неверный ввод

API под `coffee`: ИНН из 11 цифр, сумма 0, сумма не кратная 10 тыс. руб., пустая цель дают 400 с описанием поля. Подача черновика без согласий или с суммой вне диапазона продукта: 422 `incomplete` со списком полей в `errors`. Ни один запрос не отвечает 500.

### 7. Чужая заявка

Создать черновик под `coffee`, скопировать id, войти `logistics` и открыть `/api/applications/{id}`. Ждём 404, как у несуществующей. Сотрудник банка черновик тоже не видит: ни в очереди, ни по id.

### 8. Клиент не решает за банк

Под `coffee` `POST /api/applications/{id}/decision` или `/request-info`: 403, статус не меняется. В карточке клиента `allowed_next` не содержит `approved` и других решений банка, кнопок для них нет.

### 9. Конфликт версии

Под `coffee` два `PATCH /api/applications/{id}` черновика с одним и тем же `version`. Ждём: первый 200, второй 409 `version_conflict`, в интерфейсе предложение обновить карточку.

### 10. Реестр не отвечает

Учётка `unavailable` (ЕГРЮЛ для `0000500010` всегда отвечает 503), подать заявку. В Temporal UI у `FetchSource` для egrul растёт номер попытки, после пятой ошибки процесс записывает источник недоступным, остальные три завершены. Через 15-20 с заявка в `manual_review` с причиной `SF_SOURCE_UNAVAILABLE`. Войти `manager`: заявка в очереди, кнопка «Повторить проверки». Чтобы повтор прошёл, сначала снять сбой:

```sh
curl -X PUT localhost:8081/mocks/admin/faults -H 'Content-Type: application/json' \
  -d '{"source":"egrul","mode":"ok","inn":"0000500010"}'
```

После кнопки заявка снова в `checking`, в Temporal UI событие Update `retry-checks` и новый круг `FetchSource`; все источники ответили, и заявка остаётся в `checking`, как в сценарии 4. Без снятия сбоя заявка возвращается в `manual_review`. Повторить проверки по заявке без этой причины нельзя: 409.

### 11. Запрос уточнений и ответ клиента

Заявку из сценария 10 в `manual_review` открыть под `manager` (или `underwriter`), запросить документы с комментарием. Ждём: `need_info` со сроком ответа, у клиента статус «Нужны уточнения» без перезагрузки. Под `unavailable` загрузить выписку (кнопка «Взять пример выписки»), подтвердить итоги, ответить. Заявка уходит в `checking` и проходит проверки заново. В Temporal UI Update `request-info`, затем `provide-info`. Ответ с выпиской, итоги которой клиент не подтвердил: 422.

Второй способ попасть в `need_info`: перед подачей под `coffee` включить `{"source":"egrul","mode":"not_found","inn":"0000100012"}`, заявка встанет в `need_info` с `SF_NOT_FOUND`. Снять: тот же запрос с `"mode":"ok"`.

### 12. Клиент не ответил

Довести заявку до `need_info` (сценарий 11) и ничего не делать 3 минуты (`NEED_INFO_TTL`). Ждём: `expired`, карточка предлагает подать новую заявку. В Temporal UI сработавший таймер и переход, процесс завершён.

### 13. Отмена клиентом

Заявка в `need_info`, клиент отменяет её. Ждём: `cancelled_by_client`, процесс в Temporal UI завершён, в журнале заявки автор и время отмены. Отмена после того, как банк начал работу и заявка не ждёт клиента: 409.

### 14. Срок специалиста

Заявку в `manual_review` (сценарий 10) не трогать 5 минут (`REVIEW_SLA`). Ждём: в журнале у сотрудника событие эскалации от системы, статус не меняется, процесс продолжает ждать сотрудника.

### 15. Живой статус в двух кабинетах

`unavailable` в одном браузере, `manager` в другом, оба на карточке одной заявки. Сотрудник запрашивает уточнения: клиент видит новый статус без перезагрузки, и наоборот, ответ клиента сразу виден сотруднику. Поток: `GET /api/events`, события `status` и `document`.

### 16. Документы без распознавания

Стенд без профиля `ai`. Загрузить выписку к черновику или по запросу банка. Ждём: документ сразу `skipped`, клиент вводит итоги руками и подтверждает. Нестыкующиеся итоги (остаток на начало плюс приход минус расход не равен остатку на конец): 422 с полями. Файл не PDF, PNG или JPEG по содержимому, или больше 10 МБ: отказ при загрузке.

### 17. Распознавание

Стенд с `--profile ai` (README). Загрузить пример выписки любого формата. Ждём: статус документа меняется без перезагрузки, поля подставлены и подсвечены, клиент правит и подтверждает. В Temporal UI отдельный процесс `RecognizeWorkflow` с id `doc-<id документа>` на очереди `docs`, процесс заявки его не ждёт. Остановить `docs-worker` посреди работы: заявки продолжают идти.

## Появятся со скорингом, решением и подписанием

| Сценарий | Учётка | Что ждём |
|---|---|---|
| Одобрение | `coffee`, оборотный 2,5 млн на 24 мес | `approved` на запрошенных условиях, ставка, платёж, коды причин и главные факторы |
| Встречное предложение | `logistics`, оборудование 6 млн на 36 мес | `counter_offer` с меньшей суммой и большим сроком, причины изменения |
| Отказ | `build`, оборотный 5 млн | `rejected`, сотрудник видит, какие факторы снизили балл |
| Стоп-фактор без скоринга | компания с текущей просрочкой 90+ дней в БКИ | отказ на проверках, скоринг не запускается |
| Решение специалиста | `it`, оборотный 8 млн на 12 мес | запрос выписки и отчётности, `manual_review`, `underwriter` даёт встречное предложение с комментарием, клиент принимает |
| Расхождение с налоговой | `it`, профиль `ai`, файл `0000300011_statement_a_trap.pdf` | `manual_review` с `SF_DOC_MISMATCH`, сотрудник видит выручку по документу и по ФНС |
| Два решения одновременно | `underwriter` в двух браузерах | одно решение проходит, второе получает 409 |
| Подписание | любая одобренная заявка | `accepted`, `signing`, три неверных кода: выдаётся новый код, заявка остаётся в `signing`; верный код: `issued` |
| Лента | `coffee` и `logistics` рядом | разные подсказки под отрасль |

Интерфейс для этих шагов уже есть (решение специалиста, принятие условий, подписание), его можно посмотреть на моке фронта: `cd web && npm ci && npm run dev:mock`.
