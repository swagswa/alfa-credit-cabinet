# 2. Бэкенд на Go

Дата: 2026-10-20

## Статус

Принято

## Контекст

Команда из 3-4 человек, около 7 дней. Стенд должен подниматься `docker compose up` на обычном ноутбуке жюри. Рассматривали Java/Kotlin + Spring Boot, Python + FastAPI и Go.

- Java/Kotlin: мейнстрим банков, но Spring Security, очередь и BPMN-движок за неделю без сильного Spring-разработчика в команде дают риск нерабочего демо. Стенд на JVM с движком и сервером авторизации занимает 6-8 ГБ.
- Python: мало кода, но авторизацию, ретраи и воркеры всё равно пишем руками, а строгой типизации контрактов нет.
- Go: в российском финтехе уже обычный выбор (Ozon Банк, Т-Банк, платёжные сервисы WB). У части команды есть опыт.

## Решение

Бэкенд пишем на Go 1.27. Объём кода уменьшаем генерацией и готовыми библиотеками, а не фреймворком: сервер и типы из OpenAPI (oapi-codegen), процесс заявки, ретраи и таймеры у Temporal (ADR 0012), миграции у golang-migrate, SQL руками в файлах запросов, типизированный Go-код из них генерирует sqlc поверх pgx (ADR 0010), роли через casbin (ADR 0011). HTTP на echo (ADR 0013).

Три бинаря из одного модуля и одного образа: `cmd/api`, `cmd/worker`, `cmd/mocks`.

## Последствия

- Статический бинарь, образ distroless 20-30 МБ, 20-40 МБ RAM на процесс, быстрый старт.
- Руками пишем таблицу переходов, `Transition`, скоринг и политику, SQL-запросы, вход, workflow и activities, моки. Остальное генерируется (сервер из OpenAPI, Go-код запросов из SQL) или берётся из библиотек.
- Порог входа в генераторы: каркас с генерацией в первый день собирает один человек, остальные работают по образцу.
- Банковский мейнстрим на JVM, поэтому выбор на защите объясняем этим ADR.
