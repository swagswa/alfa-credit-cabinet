# 12. Процесс заявки на Temporal

Дата: 2026-10-20

## Статус

Принято. Заменяет ADR 0004 и 0005.

## Контекст

В ADR 0004 и 0005 процесс заявки вела своя таблица переходов, а фоновые шаги River. Это закрывало проверки и ретраи, но действия людей и сроки (клиент не ответил на запрос уточнений, контрпредложение висит без ответа) пришлось бы собирать самим: джобы по расписанию, проверки «не истёк ли срок», связь шагов между собой. Критерий жюри про enterprise и масштабирование ждёт как раз этого: долгий процесс с людьми, таймерами и ретраями, который переживает падения и виден целиком. У одного из нас есть рабочий опыт с Temporal, поэтому порог входа и риск за неделю ниже, чем казалось при выборе River.

Рассматривали:

- Своя таблица + River (ADR 0004, 0005): ноль новых контейнеров, но таймеры, ожидание людей и картину процесса пишем сами.
- Своя оркестрация без библиотек: то же самое, плюс ретраи и восстановление после падения воркера.
- BPMN-движок: Camunda 8 под Camunda License 1.0, Operaton это ещё одна JVM и Go-клиент без поддержки (ADR 0004).
- Temporal: сервер и Go SDK под MIT, ретраи, таймеры, ожидание сигналов и история каждого процесса из коробки.

## Решение

Процесс заявки ведёт Temporal. Версии на 20.10.2026: сервер 1.32.1, Go SDK `go.temporal.io/sdk` v1.50.0, UI 2.56.0, CLI 1.9.1, всё MIT.

- Один workflow на заявку: `credit.ApplicationWorkflow`, id workflow равен id заявки. Подача заявки в API стартует его, повторный старт с тем же id отклоняется сервером, это вторая защита от двойной подачи.
- Activities: проверки ЕГРЮЛ, БКИ, ФНС и внутренних данных банка параллельно, затем скоринг, кредитная политика, выдача (смоделирована). Ретраи и таймауты только через `ActivityOptions` и `RetryPolicy`, своих циклов нет. 4xx мока это `temporal.NewNonRetryableApplicationError`. Ретраи кончились, заявка уходит в ручное рассмотрение с причиной.
- Действия людей через Workflow Update с валидатором: клиент дал недостающие данные, принял контрпредложение, подписал; андеррайтер принял ручное решение. API вызывает `UpdateWorkflow` и сразу получает ошибку, если действие сейчас не к месту. Сроки через таймеры workflow: истёк срок ответа на запрос уточнений, заявка закрывается по таблице переходов. Длительности в конфиге, на демо короткие.
- Источник данных для интерфейса и аудита остаётся наш Postgres. Статус меняет только `credit.Transition(ctx, tx, appID, to, actor, reason)` из ADR 0004: `SELECT ... FOR UPDATE`, проверка по таблице переходов, аудит, `version+1`, `pg_notify` для SSE. Workflow вызывает его из activity. Шаг «поставить джобу River» из него убран. Activity идемпотентна: повтор после уже закоммиченного перехода видит статус равным целевому и ничего не делает.
- Таблица переходов, `AllowedNext(status, role)` для кнопок и проверки, golden-тест диаграммы состояний остаются как в ADR 0004.
- Код workflow детерминированный: без `time.Now`, `rand`, горутин и I/O, вместо них `workflow.Now`, `workflow.NewTimer`, `workflow.Go`. Всё внешнее, включая БД, только в activities. В CI `workflowcheck` (`go.temporal.io/sdk/contrib/tools/workflowcheck`).
- Тесты: workflow в `go.temporal.io/sdk/testsuite` (`TestWorkflowEnvironment`, activities подменены), сценарии таблицей и совпадают с демо-сценариями. Activities тестируются как обычные функции, с Postgres через testcontainers и моками через `httptest.Server`.
- `cmd/worker` это Temporal worker на одной task queue. API ходит в Temporal клиентом SDK.

Стенд:

- Temporal использует наш контейнер `db`, но свои базы `temporal` и `temporal_visibility`. Образ `temporalio/auto-setup` больше не используется (последний тег под сервер 1.23), официальный пример compose (`temporalio/samples-server`, каталог `compose`) делает так: одноразовый `temporalio/admin-tools` создаёт базы и накатывает схему через `temporal-sql-tool` (`DB=postgres12`, `POSTGRES_SEEDS=db`), после него `temporalio/server` (порт 7233), одноразовый контейнер создаёт namespace `default`, `temporalio/ui` (порт 8080 в контейнере). Пробрасываем UI на 8233, как у dev-сервера.
- Локально без compose: `temporal server start-dev` (gRPC 7233, UI 8233), worker и api запускаются из IDE.
- RAM: сервер 300-500 МБ, UI 50-100 МБ. Базовый стенд вырастает с 0.3-0.5 до 0.8-1.1 ГБ, замеряем `docker stats`.

## Последствия

- Ретраи, таймеры, ожидание людей и восстановление после падения воркера не пишем. Шаги процесса читаются одной функцией workflow.
- На демо Temporal UI показывает историю каждой заявки: какие проверки шли, что ретраилось, где ждали клиента.
- Масштабирование: api и worker stateless, воркеров добавляем репликами, задачи раздаёт task queue. Сервер Temporal в проде выносится отдельно и масштабируется сам.
- Плюс четыре сервиса в compose (два из них одноразовые) и около 0.5 ГБ памяти.
- Два места хранения состояния: история в Temporal, статус в `applications`. Правило: интерфейс и аудит читают только Postgres, Temporal решает, что делать дальше, статус пишет только `Transition`.
- Риск: недетерминизм. Обращение к часам, случайности или сети из workflow ломает реплей. Гасим правилом выше, `workflowcheck` и ревью, workflow держим тонким, логика в `internal/credit` и `internal/scoring`.
- Риск: версионирование. Изменение логики workflow ломает реплей уже запущенных заявок. До релиза стенд поднимаем с чистой базой, дальше ветки через `workflow.GetVersion` и тест реплея на сохранённых историях (`worker.NewWorkflowReplayer`).
- Риск: Postgres 18. Официальный пример гоняет Temporal на Postgres 16, на 18 проверяем в первый день. Если схема не встанет, Temporal получает отдельный контейнер `postgres:16`.
- Kafka, если дойдём, подключается activity публикации события после перехода, ядро не меняется.
