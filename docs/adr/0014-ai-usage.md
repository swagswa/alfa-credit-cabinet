# 14. Где используем LLM и где нет

Дата: 2026-10-21

## Статус

Принято. Уточняет ADR 0009: решение LLM не пересказывает, объяснение собирается из шаблонов.

## Контекст

Кейс приветствует ИИ и распознавание документов, но только если они дают ценность и не заменяют рабочий основной сценарий. LLM только с открытыми весами, без платных API, всё на стенде жюри. Ноутбук жюри без GPU, значит модель маленькая и работает на CPU.

Свойства LLM, которые определяют границы:

- ответ недетерминирован между версиями модели и сборками, даже при temperature 0;
- модель уверенно ошибается: путает строки, придумывает цифры, которых нет в документе;
- решение по кредиту должно раскладываться на факторы и коды причин, это ждут и клиент, и регулятор (объяснимость, проверяемость, воспроизводимость решения по сохранённым данным).

Где LLM реально нужна: там, где вход неструктурированный. У нас это документы клиента. Выписка из другого банка и бухотчётность приходят PDF или фотографией, у каждого банка своя вёрстка, и правилами на регулярках их не разобрать.

Рассматривали:

- LLM в скоринге или в решении: отпадает по всем трём свойствам выше.
- Объяснение решения через LLM (пересказ разбивки скоринга): текст красивее, но может добавить причину, которой нет в решении, или потерять ту, что есть. Клиенту это уже обещание банка. Шаблоны по кодам причин (раздел 6.4 модели процесса) дают тот же смысл, проверяются тестом и не требуют профиля `ai`.
- Распознавание через VLM (Qwen3-VL читает скан напрямую): меньше шагов, но 8B на CPU это минуты на страницу и 6+ ГБ RAM.
- Tesseract + LLM по тексту: OCR только для сканов, на текстовых PDF его нет вовсе, LLM 4B получает обычный текст и заполняет схему.

## Решение

- LLM используем только для извлечения полей из документов клиента (выписка по счёту, бухотчётность). Модель `qwen3:4b-instruct-2507-q4_K_M` (Qwen3-4B-Instruct-2507, Apache-2.0) в Ollama 0.40.7 (MIT), локально, compose-профиль `ai`.
- Скоринг, стоп-факторы, кредитная политика и объяснение решения детерминированные, без LLM. Объяснение это шаблоны по кодам причин с подстановкой чисел.
- Опционально, если успеем: подбор продукта по свободному тексту. LLM только достаёт из текста цель, сумму и срок в JSON по схеме, продукт выбирают наши правила подбора. Кнопки целей остаются основным способом.
- Ограничители распознавания:
  - ответ модели ограничен JSON-схемой через `format` Ollama, `temperature` 0;
  - после модели детерминированная проверка в Go: типы, диапазоны, ИНН документа равен ИНН заявки, суммы сходятся (входящий остаток + приход - расход = исходящий, сумма помесячных оборотов = приход);
  - человек в контуре: распознанные значения подсвечены в форме, клиент подтверждает или правит, в скоринг идут только подтверждённые;
  - сверка с данными ФНС: расхождение больше 20% это код `SF_DOC_MISMATCH` и ручное рассмотрение;
  - для аудита храним файл, сырой ответ модели, подтверждённые значения, имя модели и digest.
- Фолбэк: `AI_ENABLED=false`, Ollama не поднята, таймаут или ошибка проверки: клиент вводит значения руками. Распознавание идёт отдельным workflow, заявка его никогда не ждёт.
- Качество меряем, а не обещаем: синтетические документы трёх форматов с эталонным JSON, `make eval-docs` пишет точность по полям и форматам в `docs/ai-eval.md`.

## Последствия

- Решение по заявке воспроизводимо по сохранённым данным и не зависит от того, поднят ли профиль `ai`.
- Без профиля `ai` основной сценарий проходит целиком, меняется только ввод цифр из документа.
- Плюс Ollama на 3-4 ГБ RAM в профиле `ai` и Tesseract в образе воркера: воркер собирается на `debian:trixie-slim` вместо distroless, образ больше примерно на 100 МБ (оценка).
- Распознавание на CPU занимает десятки секунд (оценка 20-60 с на документ), поэтому в интерфейсе это фоновый шаг со статусом, а не спиннер на кнопке.
- Риск: на реальных выписках точность ниже, чем на нашей синтетике, у банков десятки вёрсток. Человек в контуре и сверка с ФНС остаются обязательными и в проде.
- Смена модели это новая строка в `docs/ai-eval.md` до мержа: прогон eval на том же наборе.
