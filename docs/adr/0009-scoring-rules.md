# 9. Балльный скоринг на правилах в YAML

Дата: 2026-10-20

## Статус

Принято

## Контекст

Кейс разделяет скоринг (насколько рискован заёмщик) и кредитное решение (что предлагаем клиенту). Решение не бинарное: одобрение, контрпредложение, запрос документов, ручное рассмотрение, отказ. Решение должно быть объяснимым для клиента и сотрудника. Реальных данных для обучения модели нет, только синтетика.

## Решение

- Скоринг: балльная модель. Факторы, пороги и баллы в `rules/scoring.yaml`, код в `internal/scoring` их только читает. На выходе балл, класс риска и вклад каждого фактора.
- Политика отдельно, в `rules/policy.yaml`: балл, продукт, сумма, срок и стоп-факторы проверок дают исход и условия. Один балл может давать разные условия для разных продуктов из `rules/products.yaml`.
- В YAML только данные: числа, списки, фиксированный набор операторов. Выражений и своего мини-языка нет.
- У правил есть `version`. Каждое решение хранит версию политики, разбивку скоринга и коды причин.
- Тест-кейсы скоринга в `testdata/scoring_cases.yaml` совпадают с демо-компаниями, по одной на каждый исход. Различающую способность модели показываем на синтетической выборке (Gini/AUC).

## Последствия

- Объяснимость без ML и без LLM: любое решение раскладывается на факторы.
- Изменение порога это правка YAML отдельным коммитом, история политики читается в git.
- ML не берём: на синтетике модель выучит наш же генератор, а объяснять её решения сложнее. Путь развития: заменить расчёт балла моделью, сохранив разбивку по факторам и отдельную политику.
- LLM, если включена, только пересказывает готовое решение простым языком и на него не влияет.
