# 10. Доступ к БД: pgx + sqlc, миграции golang-migrate

Дата: 2026-10-20

## Статус

Принято. Раздел про отсутствие слоя repository заменён [0015](0015-layers.md): `*db.Queries` вызывает только `internal/repo`.

## Контекст

Первый вариант стека брал sqlc и goose. При разборе команда сначала решила обойтись pgx и SQL строками в Go, чтобы не тащить второй генератор. В тот же день пересмотрели: таблиц десяток, но запросов к ним будет несколько десятков, и почти каждый на pgx руками это строка SQL, структура под строку, `RowToStructByName` и интеграционный тест, который ловит опечатку в имени колонки. sqlc закрывает это на этапе генерации, а SQL при этом остаётся обычным SQL в отдельном файле. golang-migrate оставляем: команда знает его по рабочим проектам, а sqlc читает его файлы миграций как схему.

## Решение

- Драйвер pgx v5. Пул (`pgxpool`) и транзакции (`pgx.BeginFunc`, `pool.BeginTx`, где нужен уровень изоляции) остаются на pgx напрямую.
- Запросы пишем руками в `internal/db/queries/*.sql`, по файлу на предметную область (`applications.sql`, `users.sql`). Каждый запрос с аннотацией `-- name: ApplicationForClient :one`.
- sqlc v1.31.1 (MIT) генерирует из них типизированный Go-код в пакет `internal/db`: `db.go`, `models.go`, `*.sql.go`. Схему sqlc берёт из `migrations/` (файлы `.down.sql` пропускает). Конфиг `sqlc.yaml` в корне: `engine: postgresql`, `sql_package: pgx/v5`, `emit_json_tags: false` (наружу модели БД не отдаём, ответы API это типы oapi-codegen), override `uuid` на `github.com/google/uuid` и `timestamptz` на `time.Time`.
- Версия sqlc закреплена в `go.mod` директивой `tool` (`go get -tool github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1`), запуск через `//go:generate go tool sqlc generate` в `internal/db/generate.go`. sqlc собирается с cgo (парсер `pg_query_go`), поэтому нужен C-компилятор: в CI и на Linux/macOS он есть, на Windows без gcc запускаем образ `sqlc/sqlc:1.31.1` той же версии.
- Сгенерированный код коммитим, CI гоняет `go generate ./...` и `git diff --exit-code`.
- Доменный код вызывает `*db.Queries` напрямую. Слоя repository поверх `Queries` нет, интерфейс объявляет потребитель, если нужна подмена. Внутри транзакции запросы идут через `db.New(tx)`: `credit.Transition` принимает `pgx.Tx` и делает `q := db.New(tx)`.
- Владение заявкой проверяется в самом запросе (`WHERE id = $1 AND company_id = $2`), `pgx.ErrNoRows` домен превращает в `ErrNotFound`.
- Необязательные фильтры списков через `sqlc.narg` (`sqlc.narg('status')::text IS NULL OR status = sqlc.narg('status')`). Если запрос так не выразить, пишем его на pgx в пакете `internal/db` рядом со сгенерированными и покрываем интеграционным тестом.
- Миграции golang-migrate v4 (MIT): файлы `migrations/NNNNNN_name.up.sql` и `.down.sql`, встроены через `embed`, источник `source/iofs`, драйвер `database/pgx/v5`. Применяются библиотекой при старте `api`, драйвер берёт advisory lock, поэтому одновременный старт реплик безопасен. Применённую миграцию не правим, пишем следующую.
- Ограничения (CHECK, UNIQUE, FK) живут в схеме, а не только в коде.

## Последствия

- Опечатка в колонке, неверное число параметров или несовпадение типов ломают `go generate`, а не запрос на стенде. Сканирования строк руками нет.
- SQL остаётся SQL: `FOR UPDATE`, CTE и `pg_notify` пишутся как есть и читаются в одном файле, жюри видит запросы без ORM.
- Новый запрос это шаг генерации и отдельный коммит со сгенерированным кодом. Каркас с генерацией в первый день собирает один человек, остальные пишут запросы по образцу.
- Динамические запросы sqlc выражает хуже, для них оставлен pgx.
- sqlc тянет свои зависимости в граф модулей через `tool`, и на Windows без gcc нужен Docker для генерации.
- Интеграционные тесты на testcontainers-go остаются для запросов с логикой: владение, `FOR UPDATE`, переходы статусов.
- `.gitattributes` помечает сгенерированный код sqlc, oapi-codegen и openapi-typescript.
