# 17. Модульный монолит, распознавание документов в отдельном воркере

Дата: 2026-10-21

## Статус

Принято. Уточняет ADR 0012, 0014 и 0015.

## Контекст

Вопрос, делить ли бэкенд на микросервисы. Кандидаты по предметной области: заявки, проверки, скоринг и решение, выдача, кабинеты клиента и банка. Почти всё это держится на одной транзакции `Transition`: статус, аудит, `version+1` и уведомление пишутся вместе, а критерий жюри «согласованность модулей» требует, чтобы статус менялся последовательно. Отдельные сервисы со своими базами превратили бы это в saga и дублирование данных, добавили бы контракты между сервисами, память на стенде и точки отказа на демо. Скоринг это чистая функция от данных и YAML, сетевой вызов к нему только добавит задержку.

Распознавание документов устроено иначе. Нагрузка другая: модель на CPU занимает все ядра, параллельность 1, память 3-4 ГБ. Образ другой: Tesseract на Debian против distroless. Отказ не должен задевать заявку, и по ADR 0014 заявка распознавание не ждёт. У него уже своя task queue `docs` и свой workflow, со всем остальным оно общается только через Temporal и Postgres.

## Решение

Модульный монолит: один репозиторий, один `go.mod`, общий код в `internal` и `pkg`, но несколько развёртываемых процессов.

| Процесс | Что делает | Образ |
|---|---|---|
| `api` (`cmd/api`) | HTTP, SSE, старт workflow | distroless |
| `worker` (`cmd/worker`) | task queue `credit`: `ApplicationWorkflow` и его activities | distroless |
| `docs-worker` (`cmd/docs-worker`) | task queue `docs`: `RecognizeWorkflow` и activity `Recognize`, `MaxConcurrentActivityExecutionSize: 1` | `debian:trixie-slim` с `tesseract-ocr-rus` |
| `mocks` (`cmd/mocks`) | симулятор внешних систем | distroless |

- `docs-worker` вместе с `ollama` и `ollama-pull` живёт в compose-профиле `ai`. Без профиля его нет, `AI_ENABLED=false`, api не стартует `RecognizeWorkflow`, документ получает `skipped`, клиент вводит итоги руками.
- Воркеры собираются из тех же `internal/worker`, `internal/usecase`, `internal/repo`; различается только, что регистрирует `main`. Пишут в ту же базу через те же репозитории.
- Микросервисы по предметной области не выделяем. Границы для будущего разреза уже проведены: слои из ADR 0015, task queue на каждый тип работы, связь между процессами только через Temporal и Postgres.

## Последствия

- Основной воркер и api лёгкие, без Tesseract. Тяжёлый модуль масштабируется и падает отдельно: на демо можно остановить `docs-worker`, и заявки продолжат идти.
- Реплики `api` и `worker` добавляются без изменений кода, задачи раздаёт Temporal.
- Один Dockerfile с тремя целями вместо двух, ещё один сервис в compose.
- Путь дальше: когда у модуля появится своя команда или своя нагрузка (например, GPU для распознавания или выдача с реальными проводками), он уходит в отдельный сервис со своей схемой БД по той же границе. До этого держим один репозиторий и одну базу.
