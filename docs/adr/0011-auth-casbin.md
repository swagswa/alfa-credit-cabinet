# 11. Свой вход на JWT и роли через casbin вместо Keycloak

Дата: 2026-10-20

## Статус

Принято

## Контекст

Нужны роли клиент, кредитный менеджер, риск-аналитик и админ, вход по тестовым учёткам без ручных шагов и разграничение доступа к эндпоинтам. Первый вариант стека брал Keycloak и go-oidc. Это отдельная JVM на 500-800 МБ, своя БД, realm в JSON и OIDC-редиректы во фронте. Кроме того, живой статус идёт по SSE, а `EventSource` в браузере не умеет слать заголовок `Authorization`, токен пришлось бы передавать в query-строке. Для прототипа с тестовыми учётками внешний сервер авторизации избыточен.

## Решение

Вход (authN):

- Таблица `users`: логин, хеш пароля, роль, компания для клиента. Тестовые учётки в сиде.
- Пароль проверяем bcrypt (`golang.org/x/crypto`, BSD-3-Clause).
- `POST /api/login` выдаёт JWT (`github.com/golang-jwt/jwt/v5`, MIT, HS256, секрет из env, `required`, короткий срок жизни) в cookie `HttpOnly`, `SameSite=Lax`, `Secure` вне локальной машины. Выход очищает cookie.
- Cookie браузер отправляет сам, поэтому SSE работает без обходов.

Права (authZ):

- casbin v3 (`github.com/casbin/casbin/v3`, Apache-2.0), модель RBAC. `internal/auth/model.conf` и `internal/auth/policy.csv` лежат в репо и встроены через `embed`.
- Субъект это роль, объект это путь (`keyMatch2`, например `/api/applications/:id`), действие это HTTP-метод. `admin` наследует права сотрудников через `g`.
- Одна middleware: читает cookie, проверяет JWT, кладёт пользователя в `ctx`, вызывает `Enforce(role, path, method)`. Нет или битый токен даёт 401, запрет политики 403.

Чего casbin не делает:

- Владение. Клиент видит только заявки своей компании: это условие в SQL-запросе (ADR 0010), нет строки значит 404.
- Переходы статусов. Какая роль может сделать какой переход, решает таблица переходов (ADR 0004).

## Последствия

- В compose на один контейнер меньше, базовый стенд легче примерно на 0.5-0.8 ГБ, без отдельной БД и realm.
- Права ролей читаются одним файлом `policy.csv`, его легко показать на защите.
- Код входа пишем сами: логин, выдача и проверка токена, middleware. Покрываем тестами: неверный пароль, просроченный токен, чужая роль, чужая заявка.
- Отзыва токена до истечения срока нет, спасает короткий срок жизни. Это допущение описано в README.
- Путь к SSO: middleware начинает проверять токен внешнего OIDC-провайдера (Keycloak или корпоративный IdP банка) вместо своего, роль берётся из claims. Политика casbin, проверки владения и таблица переходов не меняются, таблица `users` остаётся для связи пользователя с компанией.
