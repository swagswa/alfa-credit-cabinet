# Альфа-Хак: Умный кредитный кабинет предпринимателя

План реализации кейса Альфа-Банка и Changellenge.

**Главный вопрос кейса:** как создать цифровой кредитный конвейер для малого и микробизнеса, который помогает предпринимателю пройти путь от потребности в финансировании до результата по заявке, а банку управлять этим процессом в едином продукте?

**Главный принцип:** жюри оценивает связный процесс и инженерную зрелость, а не количество фич. Сначала сквозной путь "заявка -> проверки -> скоринг -> решение -> подписание -> выдача", который реально работает, потом ИИ и украшения. Кейс от Changellenge, поэтому продуктовое обоснование (исследование, границы MVP) весит не меньше кода.

---

## Жёсткие ограничения кейса

- Клиентская часть только веб-интерфейс, мобильное приложение не принимается.
- LLM только с открытыми весами (Qwen, Llama, Mistral и т.п.). GPT, Claude, Gemini в сдаваемой версии нельзя.
- Никаких платных подписок, платных API и закрытых лицензий в проверяемой версии.
- Без доступа к системам Альфы: все внешние проверки и интеграции через моки, стабы, симуляторы.
- Данные только синтетические: клиенты, компании, сотрудники, документы, заявки, финансы.
- Весь сценарий внутри продукта: почта, мессенджеры, звонки, SMS не могут быть шагами сценария.
- Допустимые упрощения: упрощённая и явно описанная логика решения, смоделированные подписание и выдача, упрощённые контракты внешних сервисов. Все допущения должны сохранять смысл процесса.

## Критерии оценки

1. Целостность: связный процесс от обращения до результата.
2. Готовность к проверке: работающий прототип, понятные инструкции, тестовые данные.
3. UX: понятно и клиенту, и банковской стороне на каждом этапе.
4. Согласованность модулей: данные сохраняются и используются дальше, статус меняется последовательно.
5. Enterprise: безопасность, надёжность, отказоустойчивость, масштабирование, сопровождение.
6. Потенциал развития: команда обосновывает решения, их ограничения и развитие.

ИИ, распознавание документов, автоматизация приветствуются, если создают ценность и не заменяют работоспособность основного сценария.

## Этап 0. До старта (полдня)

- Роли (под 3-4 человек): бэкенд и логика процесса; фронт (два кабинета); продукт, исследование и документация; DevOps и тесты (можно совместить с бэкендом).
- Приватный GitHub-репозиторий, сразу дать доступ аккаунту жюри `alfa-hack-2026`. Коммитят все, история живая.
- Уточнить в чате хакатона: нужна ли "новостная лента под клиента" со слайда 7 и формат защиты.
- Стек (всё бесплатное и open source): FastAPI + PostgreSQL + Alembic, React + Vite + TypeScript, docker-compose, Ollama + Qwen2.5 как опциональный модуль.

## Этап 1. Исследование (1 день, по-настоящему)

- 5-7 коротких интервью с предпринимателями (знакомые ИП, владельцы малого бизнеса, бухгалтеры): как брали кредит, что раздражало, каких документов не хватало, сколько ждали ответа.
- JTBD и карта пути клиента с болями. Банковскую сторону восстанавливаем по слайдам 13-15 и открытым источникам.
- MoSCoW для состава MVP. Каждый пункт привязан к найденной боли (иначе критерий "инструменты формально").
- Артефакт: `docs/research.md` с таблицей "боль -> решение в продукте".

## Этап 2. Модель процесса (1 день, главный артефакт)

**Роли:**
- клиент (владелец или уполномоченный сотрудник);
- кредитный менеджер (сопровождает заявку);
- риск-аналитик (решения, которые не прошли автоматически);
- админ (продукты и правила).

**Продукты (3 шт.):** кредит на пополнение оборотных средств, овердрафт, кредит на оборудование. У каждого: диапазон сумм и сроков, ставки, обязательные документы.

**Диаграмма состояний заявки** (на ней держится критерий 04):

```
Черновик -> Подана -> Проверка данных -> (Нужны уточнения, цикл) -> Скоринг
  -> Решение: Одобрено | Встречное предложение | Ручное рассмотрение | Отказ
  -> Клиент принял условия -> Подписание -> Выдача -> Закрыта
```

Каждый переход пишет кто, когда и почему (журнал аудита).

**Модель данных:** компания, представитель и его полномочия, продукт, заявка, документ, результат проверки, скоринг с вкладом каждого фактора, решение, предложение, событие.

**Артефакты:** диаграмма состояний и ER-модель (Mermaid в репо), `docs/process.md` с явным списком упрощений и причин (подписание и выдача смоделированы, интеграции через моки).

## Этап 3. Архитектура

Сервисы в docker-compose:

- `api` (FastAPI):
  - машина состояний заявки: переходы валидируются в одном месте, руками статус не поменять;
  - JWT-авторизация с ролями;
  - журнал аудита;
  - идемпотентность подачи заявки;
  - health-check;
  - Swagger из коробки.
- `worker`: фоновые шаги (проверки, скоринг) через таблицу задач / outbox в Postgres, без лишнего брокера. Ретраи при сбое мока: показываем отказоустойчивость.
- `mocks`: отдельный сервис-симулятор:
  - ЕГРЮЛ / ЕГРИП: статус, дата регистрации, ОКВЭД;
  - БКИ: просрочки, долговая нагрузка;
  - ФНС "Прозрачный бизнес": выручка, налоги, массовый адрес.
  Ответы из синтетической базы по ИНН, плюс сценарии сбоя (таймаут, 500), чтобы показать ретраи.
- `web`: SPA с двумя кабинетами.
- `db`: PostgreSQL с миграциями и сидом.
- `llm`: Ollama + Qwen2.5 в отдельном compose-профиле. Основной сценарий работает без него.

Статус в реальном времени: SSE из API, клиент видит переходы без перезагрузки.

## Этап 4. Скоринг и решение (раздельно, как требует слайд 14)

- **Скоринг:** балльная модель на прозрачных правилах из YAML-конфига. Факторы: возраст бизнеса, выручка против запрошенной суммы, долговая нагрузка, просрочки в БКИ, статус в ЕГРЮЛ, налоговая дисциплина. На выходе балл, класс риска и вклад каждого фактора.
- **Кредитная политика:** балл + продукт + сумма + срок -> решение: одобрить / встречное предложение (меньше сумма, дольше срок, другой продукт) / запросить документы / ручное рассмотрение / отказ.
- Синтетические компании подобраны так, чтобы каждый исход воспроизводился своим ИНН на демо.

## Этап 5. Интерфейсы

**Кабинет клиента:**
1. Вход по тестовой учётке, выбор компании и роли представителя.
2. Подбор продукта по задаче ("на что нужны деньги") с понятным сравнением.
3. Анкета с автоподстановкой из "ЕГРЮЛ" по ИНН, загрузка документов (выписка, отчётность).
4. Трекер заявки: где она сейчас, что дальше, что нужно от клиента.
5. Ответ на запрос уточнений прямо в кабинете (не почта и не звонок).
6. Экран решения: условия, встречное предложение с кнопкой "принять", объяснение простыми словами.
7. Имитация подписания (код подтверждения внутри интерфейса) и статус "выдано".
8. Персональная лента: события заявки плюс рекомендации по профилю компании (отрасль по ОКВЭД, обороты, текущие продукты). Например: "заявка одобрена", "для вашей отрасли есть льготная программа", "пора загрузить отчётность за квартал". Закрывает "новостную ленту под клиента" со слайда 7.

**Кабинет банка:**
1. Очередь заявок с фильтрами по статусу, сроку, риску.
2. Карточка заявки: данные, результаты проверок, разбивка скоринга, журнал аудита.
3. Действия: запросить документы, принять ручное решение с комментарием, изменить условия.
4. Простой дашборд: сколько заявок на каком этапе, среднее время до решения.

## Этап 6. ИИ (только там, где реально полезно)

Открытые веса, локально через Ollama:
- **Распознавание документов:** выписка или баланс -> поля анкеты. Надёжный путь: текстовый PDF или OCR через Tesseract, затем LLM разбирает в JSON по схеме.
- **Объяснение решения клиенту:** разбивка скоринга -> человеческий текст ("одобрили меньшую сумму, потому что...").
- **Помощник по подбору продукта** (опционально).

У каждой функции есть фолбэк без LLM (флаг `AI_ENABLED`). Это прямое требование кейса, и об этом нужно сказать на защите.

## Этап 7. Качество

- pytest: все переходы машины состояний (включая запрещённые), скоринг и политика на фиксированных компаниях, API.
- E2E на Playwright: сквозной happy-path и сценарий со встречным предложением.
- GitHub Actions: линт, тесты, сборка образов.
- Lock-файлы: `uv.lock` или `poetry.lock`, `package-lock.json`. Фиксированные версии образов, без `latest`.

## Этап 8. Комплект на сдачу (чек-лист по слайду 7)

- [ ] `docker compose up` поднимает всё на чистом ПК, сид загружается сам.
- [ ] `README.md`: назначение, архитектура, требования к окружению, запуск, `.env.example` и переменные окружения, описание компонентов, пошаговый сценарий проверки с тестовыми учётками и ИНН под каждый исход.
- [ ] `docs/`: архитектурная схема, диаграмма состояний, ER-модель, описание API, тестовые сценарии, исследование.
- [ ] OpenAPI (`/docs`) плюс коллекция запросов (Postman или Bruno) в репо.
- [ ] `THIRD_PARTY_NOTICES`: библиотеки, модель Qwen и её лицензия, список смоделированных интеграций (ЕГРЮЛ, БКИ, ФНС, подписание, выдача).
- [ ] Только синтетические данные, ни одного реального ИНН или ФИО.
- [ ] Деплой на бесплатный сервер с публичной ссылкой (LLM можно не поднимать, если сервер слабый).
- [ ] Git-тег `v1.0-final` и commit hash до дедлайна. После дедлайна не пушить.

## Этап 9. Защита

- Демо около 5 минут: предприниматель подаёт заявку -> автоподстановка по ИНН -> банк запрашивает документ -> клиент догружает в кабинете -> встречное предложение -> клиент принимает -> подписание -> "выдано". Параллельно на втором экране кабинет банка обновляется вживую.
- Показать, как персональная лента отличается у двух разных компаний (например, кофейня и логистика).
- Слайды по критериям жюри: боли из интервью -> решения в продукте, границы MVP и почему, архитектура и надёжность, ограничения и развитие (реальные интеграции, ML-скоринг, ЭЦП).
