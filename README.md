# Кредитный кабинет предпринимателя

Прототип для кейса Альфа-Банка на Альфа-Хак 2026: клиент подбирает кредит и ведёт заявку, банк в своём кабинете проводит её через проверки, скоринг и решение.

На сервере сейчас работают вход, подбор продукта, компания по ИНН, черновики, подача, документы с распознаванием, проверки в ЕГРЮЛ, ФНС, БКИ и данных банка (моки на фикстурах), очередь банка, запрос уточнений, ответ клиента, повтор проверок, стоп-факторы, скоринг, решение политики и решение андеррайтера, принятие условий, договор с графиком, подписание кодом, смоделированная выдача и закрытие, отмена и живые события. Фронт умеет всё это и на своём моке API (см. ниже).

## Запуск

Нужен Docker с compose v2, больше ничего ставить не надо. Первая сборка Go и фронта идёт несколько минут, Docker стоит дать от 4 ГБ памяти; поднятый стенд сам ест меньше 1 ГБ. Профилю `ai` нужно ещё около 4 ГБ памяти и 3 ГБ диска под модель. GPU необязателен: compose его в Ollama не пробрасывает, модель считает на CPU, и документ распознаётся заметно дольше, чем в замере из `docs/ai-eval.md`.

```sh
docker compose up -d --build --wait
```

| Что | Адрес |
|---|---|
| Фронт | http://localhost:8000 |
| API | http://localhost:8080/api, проверка: `/api/health` |
| Swagger UI | http://localhost:8000/swagger/, «Try it out» ходит в тот же api; закрытые операции после `POST /login` из самого Swagger |
| Temporal UI | http://localhost:8233 |
| Моки внешних систем | http://localhost:8081, проверка: `/health` |
| Postgres | localhost:5432, база `credit`, пользователь и пароль `credit` |
| Temporal (gRPC) | localhost:7233 |

Порты 8080, 8081, 8233 и 7233 в `compose.yaml` зашиты, через `.env` меняются только `DB_PORT` и `WEB_PORT`. Если какой-то из них занят, переложи его в своём `compose.override.yaml` (compose подхватит его сам, в git он не нужен), например моки на 8091:

```yaml
services:
  mocks:
    ports: !override
      - "8091:8081"
```

Тогда и в командах ниже вместо `localhost:8081` подставляй свой порт.

Распознавание документов (Ollama, Qwen3-4B, Tesseract) в отдельном профиле, при первом запуске скачивается модель около 2,5 ГБ:

```sh
AI_ENABLED=true docker compose --profile ai up -d --build --wait
```

Метрики, логи и трейсы (Prometheus, Grafana, Loki, Jaeger) тоже в отдельном профиле, подробности в разделе «Наблюдаемость»:

```sh
make up-obs
```

В контейнеры compose их не прокидывает, так что в `.env` они ничего не меняют, работают только при запуске процесса руками.

## Вход

Сессии серверные: при входе `api` заводит сессию в Redis, в cookie `session` уходит подписанный токен с её номером. Выход удаляет сессию, токен сразу перестаёт работать. Попыток входа с одного адреса не больше `LOGIN_ATTEMPTS` за `LOGIN_WINDOW` (по умолчанию 10 в минуту). На стенде по http `COOKIE_SECURE=false`, за https его нужно включить, иначе cookie будет уходить открытым текстом.

## Как проверить

Пошаговые сценарии с учётками и ожидаемым результатом в [docs/test-scenarios.md](docs/test-scenarios.md), там же отмечено, чего на стенде не воспроизвести. Ход каждой заявки виден в Temporal UI, id процесса равен id заявки.

Короткий путь до выдачи в интерфейсе, минут пять:

1. http://localhost:8000, вход `coffee` / `demo12345`. Новая заявка: оборотный кредит 2,5 млн на 24 месяца, выручка 1,2 млн в месяц, загрузить паспорт руководителя (любой PDF), отметить оба согласия, подать.
2. Секунд через 10 статус `approved`: 2,5 млн, 24 мес, 19%, платёж около 126 тыс. Во втором браузере (или приватном окне) `manager` видит заявку в очереди, в её карточке балл 87 и разбивка по факторам.
3. Принять условия. Через пару секунд `signing`, в документах договор `dogovor-<номер>.pdf` с графиком.
4. Получить код: он показан прямо в карточке. Ввести неверный, увидеть остаток попыток, затем верный.
5. `issued`, через минуту (`CLOSE_AFTER`) `closed`. В журнале заявки (он в карточке у `manager`, клиенту журнал не показываем) весь путь, в Temporal UI шаги процесса.

Ручное рассмотрение и решение андеррайтера проходит `it` (сценарий 21), встречное предложение `logistics`, отказ `build`, сбой реестра `unavailable`. Если не успел принять условия или подписать за 5 минут, заявка уходит в `expired`, подай новую.

Тот же путь через API лежит коллекцией Bruno: вход клиента, продукты и подбор, компания по ИНН, черновик с `Idempotency-Key` и его повтор, согласия, загрузка и подтверждение выписки, подача, карточка, журнал, отмена второго черновика; затем заявка `unavailable` уходит в ручное рассмотрение, менеджер находит её в очереди, запрашивает уточнения, клиент отвечает, менеджер повторяет проверки; выход клиента; андеррайтер даёт контрпредложение, клиент принимает его, берёт код, один раз ошибается и подписывает; карточка выданной заявки, договор и его PDF, лента, отмена поданной заявки, закрытие выданной. На поднятом стенде:

```sh
cd collections/credit-cabinet
npx -y @usebruno/cli@4.2.1 run --env local --disable-cookies
```

Прогон около 2,5 минут: 20 с паузы на ретраи ЕГРЮЛ (`checksWaitMs`) и 65 с ожидания закрытия после выдачи (`closeWaitMs`, на стенде `CLOSE_AFTER=1m`). Если поменял сроки в `.env`, поправь паузы в `environments/local.bru`; если поменял `WEB_PORT`, добавь `--env-var webUrl=http://localhost:<порт>/api`, иначе упадёт шаг с примером выписки. Коллекция входит четыре раза, а лимит 10 входов в минуту на адрес общий с браузером и e2e: прогон сразу после другого или рядом с e2e может получить 429 на входе, тогда подожди минуту. Без `--disable-cookies` CLI подставляет cookie последнего входа поверх явного заголовка, и шаги клиента уходят с сессией менеджера. Ту же папку можно открыть в приложении Bruno. Живые события коллекция не держит, их удобнее смотреть curl:

```sh
curl -s -c jar -H 'Content-Type: application/json' -d '{"login":"coffee","password":"demo12345"}' localhost:8080/api/login
curl -N -b jar localhost:8080/api/events
```

## Допущения и упрощения

Частные допущения описаны ниже рядом с функцией (заявки, моки, документы, распознавание). Общие для прототипа:

- внешние источники (ЕГРЮЛ/ЕГРИП, ФНС, БКИ, данные банка) заменены моками на синтетических данных; суды, ФССП, ЕФРСБ, санкционные списки и проверки по 115-ФЗ не моделируем;
- клиенты, компании, документы и обороты синтетические, ИНН демо-компаний с префиксом `0000`, на любой другой корректный ИНН мок отвечает компанией из генератора (см. «Моки внешних систем»);
- скоринг считается балльной моделью по `rules/scoring.yaml`, политика задана таблицей класс x продукт в `rules/policy.yaml`; воркер читает их при старте, кривой файл не даёт ему подняться, а версия правил пишется в каждое решение;
- решение считается заново на каждом проходе проверок, старое решение андеррайтеру после повторных проверок не показываем;
- андеррайтер выбирает коды причин сам; тексты клиенту берутся из расчёта политики, который он видел, код, которого в расчёте не было, клиент не увидит (банк видит код);
- подписание и выдача смоделированы: код приходит уведомлением в кабинете (колокольчик) вместо СМС, электронной подписи файла нет и хэш договора к подписи не привязан, выдача сводится к строке в `payouts` на счёт из данных банка, без проводок и движения денег; в проде код уходит СМС через шлюз банка (простая электронная подпись) или договор подписывается УКЭП, выдача идёт через АБС с открытием ссудного счёта;
- `closed` значит, что заявка завершена, наступает по таймеру `CLOSE_AFTER` после выдачи; обслуживание и погашение кредита за границей прототипа;
- договор с графиком собирается из шаблона один раз после принятия условий, условия после этого не меняются;
- документы на подлинность не проверяем, распознаём только итоговые поля выписки и отчётности, подделку ловит только сверка выручки с ФНС;
- все сроки (уточнение, ручное рассмотрение, принятие условий, подпись, закрытие) на демо в минутах и без производственного календаря, прод-значения в таблице переменных выше;
- черновики не истекают, процесс заводится только при подаче;
- уведомления только в интерфейсе (колокольчик, карточка и SSE), почты, СМС и мессенджеров в сценарии нет; текст уведомления с кодом подписи на стенде хранится как есть, в проде код в ленте маскируется после ввода или по сроку;
- у пользователя одна роль, у представителя одна роль в компании, его полномочия подача не сверяет.

## Заявки

Клиент создаёт черновик по ИНН (`POST /api/applications` с заголовком `Idempotency-Key`), правит его (`PATCH` с `version` из карточки) и может отменить до подачи. Повтор с тем же ключом отдаёт ту же заявку, тот же ключ с другим телом даёт 409 `idempotency_conflict`. На устаревшую `version` ответ 409 `version_conflict`, обнови карточку и повтори. Чужая заявка отвечает 404, как несуществующая. В ответе `allowed_next`: куда текущий пользователь может перевести заявку, по нему фронт рисует кнопки.

Подача `POST /api/applications/{id}/submit` сверяет анкету с условиями продукта из `rules/products.yaml` и требует оба согласия, `bki_consent` и `pd_consent` (ставятся в черновике, момент согласия пишется в базу). Что не так, приходит 422 `incomplete` со списком полей в `errors`. Дальше `draft -> submitted` и старт `ApplicationWorkflow` с id процесса, равным id заявки. Процесс стартует после коммита перехода, поэтому если Temporal не ответил, заявка остаётся в `submitted`, а клиент получает 503: повторная подача просто дозапускает процесс. Повтор по уже идущему процессу отвечает 200 с карточкой, второго workflow не появляется.

Допущения:

- компания, которой у нас ещё нет, заводится по выписке ЕГРЮЛ из мока, автор заявки становится её представителем в указанной роли; полномочия (руководитель из ЕГРЮЛ, доверенность для `proxy`) подача пока не сверяет, загруженная доверенность идёт в заявку как документ без автоматической проверки;
- к компании, у которой уже есть представитель, сам себя не добавишь: 403. Второго представителя на стенде заводит только сид;
- роль представителя одна на человека и компанию, правка роли в черновике меняет её и для других его заявок по этой компании;
- полноту анкеты и диапазоны продукта черновик не проверяет, только схема API: это делает подача;
- среднемесячную выручку подача не требует: нужна ли она, видно только по нашим оборотам, это решает шаг проверки;
- согласия в анкете хранятся флагами с моментом согласия, без версии текста. Согласие на БКИ при подаче становится записью `bki_consents` со своим id и датой из анкеты, бюро принимает его полгода с этой даты (218-ФЗ, ст. 6). Если бюро отказало, проверка БКИ пишется как `unavailable` с причиной и заявка уходит на ручной разбор, как при недоступном источнике;
- черновик отменяет сам `api`, поданную заявку отменяет процесс: после `accepted` и в работе у банка отмена даёт 409.

Действия по поданной заявке (`provide-info`, `request-info`, `retry-checks`, `decision`, `accept`, `sign`, `cancel`) `api` передаёт в `ApplicationWorkflow` как Update и ждёт, пока процесс их исполнит, в ответе уже новая карточка. Действие не к месту (не тот статус, заявка как раз меняется, процесс уже закончился) отклоняет валидатор процесса с 409 `illegal_transition`. В ответе клиента документы годятся только подтверждённые или нераспознаваемые, иначе 422; уточнённая выручка пишется в анкету до перехода. Что именно запрошено, карточка отдаёт в `info_request`: виды документов, причины с текстом и комментарий сотрудника из `request-info`, срок тот же, что `due_at`. По стоп-фактору документы берутся из недостающих по правилам продукта. Причины, которые процесс ставит сам ещё до расчёта решения (`SF_NOT_FOUND`, недоступный источник), идут без текста: клиент их не видит, банк видит код. Ответ клиента, срок или отмена запрос закрывают, после `provide-info` поля в карточке нет.

Очередь банка: тот же `GET /api/applications`, у `manager`, `underwriter` и `admin` в нём все поданные заявки, у клиента только его компаний, фильтры и сортировка общие. Черновик банку не виден ни в очереди, ни в карточке, ни в событиях: до подачи нет согласия на обработку данных, и делать с ним банку нечего. `sort=due_at` ставит сверху ближайший срок шага, `sort=score` самые рискованные, заявки без срока или без балла уходят в конец. В карточке сотрудник дополнительно видит `checks`, последний ответ каждого источника. Журнал `GET /api/applications/{id}/history` отдаёт переходы по порядку с автором и кодами причин; клиенту комментарии банка и системы не показываем, только его собственные. Причины последнего решения клиент видит текстом (мягкие стоп-факторы ему не раскрываются, вместо них `R_MANUAL_RISK`), условия в `offer`. Сотрудник дополнительно видит коды без текста, балл с разбивкой по факторам, рекомендацию политики и её версию.

Решение андеррайтера `POST /api/applications/{id}/decision` принимается только из `manual_review` и только ролью `underwriter`: исход `approved`, `counter_offer` или `rejected`, комментарий обязателен. Одобрению и контрпредложению нужны условия, они проходят те же рамки продукта, что и анкета, платёж считает сервер; отказу нужна хотя бы одна причина. Неполное решение 422, не к месту (не тот статус, уже решили) 409.

Дальше клиент принимает условия `POST /api/applications/{id}/accept` с `version` из карточки: условия успели поменяться, 409 `version_conflict`. Отказаться от условий можно через `cancel`. После принятия процесс сам собирает договор с графиком платежей и переводит заявку в `signing`, договор лежит в документах заявки видом `loan_agreement` и скачивается как остальные, загрузить такой вид самому нельзя (400). Код подписи `POST .../signing-code` выдаётся только в `signing` (иначе 409), 6 цифр, 3 попытки, живёт `SIGNING_CODE_TTL`, новый код заменяет старый и возвращает попытки. `POST .../sign`: неверный код 422 с остатком попыток по полю `code`, после трёх неверных или по истечении срока код сгорает (422 «запросите новый»), нужен новый, заявка остаётся в `signing`. Верный код: выдача и `issued`, через `CLOSE_AFTER` заявка закрывается. В базе хранится только хэш кода, ни в логи, ни в журнал, ни в процесс Temporal сам код не попадает: его сверяет `api`, процессу уходит уже факт подписи. Не принял условия или не подписал за срок: `expired`.

## Лента клиента

`GET /api/feed` только для клиента: сначала подсказки по профилю компании, за ними смены статусов её заявок из журнала, новые сверху, `limit` на всё вместе. Фразы на статусы и подсказки лежат в `rules/feed.yaml`, в условии подсказки участвуют класс ОКВЭД, продукты и обороты в банке и статус последней заявки, операторы те же `gt|lt|eq|ne`. Под `coffee` и `logistics` до подачи видно разное: общепиту про господдержку, грузоперевозчику про кредит на машины; после проверки заявки добавляются подсказки по продуктам. Чужая компания в `company_id` отвечает 404.

Допущения: продукты и обороты берём из последней проверки данных банка по заявкам компании, а не живым запросом: лента перечитывается на каждое событие и съедала бы сбои, заданные моку. Поэтому до первой проверки подсказок по ним нет. Эскалации SLA в ленту не попадают, это внутреннее дело банка. На решение по заявке лента не влияет.

## Уведомления

Клиенту в кабинете, колокольчик в шапке. Пишутся в той же транзакции, что меняет статус заявки (фразы в `rules/notifications.yaml`, нет фразы на статус, нет уведомления) или выдаёт код подписи, поэтому не теряются и не приходят про откатившийся переход. Получатели: клиенты компании заявки, сотрудникам банка не пишем, у них очередь. `GET /api/notifications` (свои, новые сверху, `unread=true` только непрочитанные), `POST /api/notifications/{id}/read`, `POST /api/notifications/read-all`; чужое уведомление 404. Новое уведомление приходит по SSE событием `notification` только адресату.

## Профиль клиента

`GET /api/profile` только для клиента: контакты, как их знает банк, реквизиты его компаний, счёт для выдачи, поступления за 12 месяцев и продукты из данных банка, выданные кредиты с договором. В кабинете это раздел «Профиль». Данные банка запрашиваются при каждом открытии: если мок лежит (пульт сбоев у `admin`), профиль всё равно открывается, вместо блока банка плашка.

Допущения: всё только для чтения, правка реквизитов и контактов это отдельный процесс банка, в прототип не входит. Номер счёта генерирует мок по ИНН, тот же стоит в синтетической выписке, на него же идёт выдача.

## Устройство

Модульный монолит: один репозиторий и один Go-модуль, но четыре процесса.

| Процесс | Что делает |
|---|---|
| `api` | HTTP API и живые события (SSE), стартует процесс заявки в Temporal |
| `worker` | ведёт заявку: проверки во внешних системах, скоринг, решение, выдача |
| `docs-worker` | распознаёт выписки и отчётность, отдельно, потому что тяжёлый и с другим образом |
| `mocks` | симулятор ЕГРЮЛ/ЕГРИП, ФНС, БКИ и внутренних данных банка |

Код разложен по слоям: `internal/domain` (сущности и правила без I/O), `internal/repo` (SQL через sqlc), `internal/usecase` (логика и транзакции), `internal/api` и `internal/worker` (вход снаружи). Переиспользуемая инфраструктура в `pkg/`. Контракт API в `api/openapi.yaml`, статусы заявки в `docs/state-diagram.md`, модель данных в `docs/data-model.md`. Логи у всех процессов JSON через `pkg/logger`, ФИО и логины там маскируются на уровне core (поля `fio`, `full_name`, `login` целиком, ФИО в строках и текстах ошибок по шаблону), ИНН компании и id остаются.

Подробнее: компоненты и путь заявки в [docs/architecture.md](docs/architecture.md), обоснование решений в [docs/decisions.md](docs/decisions.md), боли клиентов и банка, источники и границы MVP в [docs/research.md](docs/research.md).

## Наблюдаемость

`make up-obs` поднимает стенд вместе с профилем `obs`. Основной сценарий от него не зависит, без профиля процессы просто не шлют трейсы.

| Что | Адрес |
|---|---|
| Grafana, дашборд «Кредитный конвейер» | http://localhost:3000, смотреть можно без входа, править под `admin`/`admin` |
| Prometheus | http://localhost:9090 |
| Jaeger | http://localhost:16686 |

Метрики: каждый Go-процесс отдаёт `/metrics` на порту 9100 внутри сети compose (наружу не открыт), там HTTP-запросы по маршрутам и кодам, activity и workflow Temporal, запросы в базу по именам запросов sqlc, пул соединений и рантайм Go. Сервер Temporal отдаёт свои на 9090. Трейсы через OpenTelemetry: один трейс идёт от запроса в api через Temporal (запуск процесса, update, activity) до моков и SQL, так что подачу заявки видно целиком, со всеми ретраями источника. Логи всех контейнеров собирает Grafana Alloy через сокет docker и складывает в Loki, уровень из JSON zap становится меткой. В строках ошибок api (5xx) есть `trace_id`, из лога в Grafana по нему открывается трейс в Jaeger. Все трейсы одной заявки в Jaeger ищутся по тегу `temporalWorkflowID=<id заявки>`: подача, действия людей и каждая activity.

На дашборде бизнес-панели (заявки по статусам, решения, просроченные шаги, выдачи) читают Postgres напрямую, технические идут из Prometheus, внизу ошибки из Loki. Чтобы было на что смотреть, хватит `make e2e`. Jaeger хранит трейсы в памяти, после рестарта они пропадают; на проде вместо него коллектор OpenTelemetry и постоянное хранилище.

Alloy читает `/var/run/docker.sock`. На Docker Desktop под Windows и macOS сокет тоже есть, но если логи не появляются, проверь, что в настройках Docker включён доступ к сокету по умолчанию.

## Синтетические документы

Для распознавания и кнопки «Загрузить пример выписки» (она отдаёт текстовую выписку формата a) лежит готовый набор в `testdata/documents`, пересобирается `make docgen`, повторный запуск даёт те же байты. Там выписки трёх форматов: a и b: текстовые PDF двух выдуманных банков с разными колонками и подписями, c: «скан» PNG с поворотом и шумом (один экземпляр завёрнут в PDF без текстового слоя). Плюс отчётность формата a и ловушка `0000300011_statement_a_trap.pdf`, где приход завышен в 1,5 раза. Рядом с каждым файлом `.truth.json` с полями, которые должно достать распознавание.

Компании: четыре демо и две из генератора (`0012345673`, `001234567887`). Один документ по любому ИНН:

```sh
go run ./cmd/docgen -inn 0000300011 -kind statement -format b -out /tmp/docs
```

Цифры считает `internal/mocks/synth`, тот же пакет кормит мок ФНС и оборотов в банке. Допущение: выручка за прошлый год в ФНС равна поступлениям по выписке за 12 месяцев (октябрь 2025 - сентябрь 2026). Иначе при росте выручки честная выписка расходилась бы с налоговой больше чем на 20% и падала в ручную проверку вместе с ловушкой.

## Моки внешних систем

`mocks` (порт 8081) отвечает за ЕГРЮЛ/ЕГРИП `GET /egrul/{inn}`, ФНС «Прозрачный бизнес» `GET /fns/{inn}`, БКИ `POST /bki/report` (тело `{inn, consent_id, consent_given_at}`, без согласия или со старым, больше 6 месяцев, 403) и внутренние данные банка `GET /internal/{inn}`. Деньги в рублях, как у настоящих источников. Демо-компании описаны в `internal/mocks/fixtures/<инн>.yaml`: реквизиты как в демо-сиде, выручка и обороты по месяцам досчитываются из `synth`, поэтому сходятся с синтетическими документами. У `0000300011` нет счёта в банке, данные банка отвечают 404, у `0000500010` ЕГРЮЛ всегда 503.

Сбои для показа ретраев включаются на ходу и живут до рестарта мока:

```sh
# фнс отвечает 500 всем; mode: ok, timeout, http_500, http_503, flaky (первые n вызовов 500), not_found
curl -X PUT localhost:8081/mocks/admin/faults -d '{"source":"fns","mode":"http_500"}' -H 'Content-Type: application/json'
# только одной компании, и снять
curl -X PUT localhost:8081/mocks/admin/faults -d '{"source":"egrul","mode":"flaky","n":3,"inn":"0000100012"}' -H 'Content-Type: application/json'
curl -X PUT localhost:8081/mocks/admin/faults -d '{"source":"fns","mode":"ok"}' -H 'Content-Type: application/json'
curl localhost:8081/mocks/admin/faults
```

То же без curl: под `admin` в кабинете раздел «Пульт сбоев» (`GET/PUT /api/admin/faults`, api ходит в мок по `MOCKS_URL`). Там сбой ставится на весь источник, `flaky` роняет три запроса, и рядом живой журнал запросов в источники по всем заявкам: видно, как процесс повторяет проверку и с какой попытки она прошла. Сбои на одну компанию пульт не показывает.

Любой другой корректный ИНН отвечает компанией из генератора (`synth.Sources`): сид из ИНН и версии генератора, одна и та же компания во всех четырёх источниках, регион в адресе по первым двум цифрам ИНН, в ответах `generator_version`, в кабинете у такой компании плашка «данные сгенерированы». Признаки (возраст, просрочки, нагрузка, недоимка, счёт у нас) коррелированы со скрытым качеством компании, распределение задано таблицей `mix` в `internal/mocks/synth/sources.go`. ИНН с неверными контрольными цифрами отвечает 404, как несуществующий.

Исходы на синтетике: типичная заявка (оборотный кредит на полторы месячные выручки на 12 месяцев, выручка в анкете как в ФНС, нужные документы приложены) по 10 000 ИНН из генератора даёт 61,4% одобрений, 19,1% встречных предложений, 9,4% ручной проверки или запроса данных и 10,0% отказов. Gini балла 0,60, AUC 0,80. Дефолт размечает сам генератор по скрытому качеству компании (вероятность от 45% у слабых до 1% у сильных, бросок по сиду из ИНН), в ответы источников разметка не попадает. Перепроверить: `go test -run TestOutcomes -v ./internal/mocks`, тест падает, если доля любого исхода уходит от 60/20/10/10 дальше чем на 5 п. п. или Gini ниже 0,5. Подгоняли только таблицей `mix`, правила скоринга и политики под синтетику не трогали.

Допущения: компаниям из генератора не меньше 13 месяцев, потому что выписка у всех за 12 полных месяцев; у кого счёта у нас нет, данные банка отвечают 404, как у `0000300011`. Админка сбоев без авторизации, мок живёт только на стенде.

## Документы заявки

Клиент грузит документ к черновику или по запросу банка (`need_info`): PDF, PNG или JPEG до 10 МБ, тип смотрим по содержимому, а не по расширению. Файл лежит в Postgres в `bytea`: файлы маленькие, бэкап и права те же, что у заявки, отдельное хранилище на демо не нужно. Выписка и отчётность с профилем `ai` уходят на распознавание, без него сразу `skipped`, остальные виды просто `uploaded`.

Итоги клиент подтверждает один раз (`POST /api/documents/{id}/confirm`), распознанные или введённые руками, разницы нет. Проверки те же, что после модели: не сошлось, 422 с ошибками по полям. Распознавание, которое дошло после подтверждения, его не перетирает. Смена статуса документа приходит в SSE событием `document`.

Подтверждённые итоги решение сверяет с выручкой ФНС за прошлый год (`domain.CheckRevenue`): выписку за N месяцев приводит к году как приход / N * 12, отчётность берёт, только если она за тот же год. Расхождение больше порога строки `SF_DOC_MISMATCH` в `rules/policy.yaml` (20%) отправляет заявку специалисту. Короткая выписка у сезонного бизнеса может дать ложное срабатывание, но это ручная проверка, а не отказ. Нет подтверждённого документа или выручки ФНС: сверки нет, решение её не ждёт.

Пример выписки рисует `mocks`, nginx отдаёт ему `/api/samples/`, api про примеры не знает:

```sh
curl -o it.png 'http://localhost:8000/api/samples/0000300011?kind=statement&format=c'
```

## Распознавание документов

Работает только в профиле `ai`: `docs-worker` на очереди `docs` берёт текстовый слой PDF, сканы прогоняет через Tesseract (`-l rus+eng --psm 6`), поля по JSON-схеме достаёт `qwen3:4b-instruct-2507-q4_K_M` в Ollama, дальше проверки в Go: ИНН совпадает с заявкой, период до 13 месяцев и не в будущем, остаток на начало плюс приход минус расход равен остатку на конец, помесячный приход сходится с итогом. Не сошлось, документ `failed` и клиент вводит итоги руками. Без профиля документ `skipped`.

Настройки `docs-worker`: `TESSERACT_PATH` (по умолчанию `tesseract` из PATH), `TESSDATA_PREFIX`, если языки не в стандартном каталоге, `OLLAMA_URL`, `OLLAMA_MODEL`, `OCR_TIMEOUT` на страницу, `OLLAMA_TIMEOUT`.

Точность меряет `make eval-docs` на `testdata/documents`, итог с моделью, digest и временем в `docs/ai-eval.md`. Локально нужны tesseract с языками rus и eng и Ollama с моделью; ollama из compose порт наружу не публикует, так что для прогона подними свою или задай `OLLAMA_URL`.

Допущения: суммы в документе в рублях, отчётность в тысячах рублей пока не поддерживаем; не больше 5 страниц; модель видит первые 12 000 символов текста.

## Проверка интерфейса без бэкенда

В каталоге web: npm ci, npm run dev:mock. Обычный npm run dev отключает мок и проксирует /api на localhost:8080. Сессии и файлы мока сбрасываются при перезапуске. Расчёты предложений и подбор в моке демонстрационные.

Перед PR: npm run lint и npm run build, их же гоняет CI.

Работа по доверенности в моке фронта: выбор роли `proxy` и загрузка документа, полномочия не сверяются (см. допущения выше).
