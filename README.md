# Кредитный кабинет предпринимателя

Прототип для кейса Альфа-Банка на Альфа-Хак 2026: клиент подбирает кредит и ведёт заявку, банк в своём кабинете проводит её через проверки, скоринг и решение.

Фронтенд поддерживает вход, заявки, документы, уточнения, предложения и учебное подписание. Для автономной разработки есть мок API. Реализация серверного конвейера развивается отдельно; готовность интерфейса на моке не означает готовности всех серверных операций.

На сервере сейчас работают вход, подбор продукта, черновики, подача, документы, очередь банка и живые события. Скоринга и решения ещё нет: заявка проходит проверки в источниках и останавливается в `need_info` или `manual_review`. Моки ЕГРЮЛ, ФНС и БКИ пока отвечают 404, поэтому компания по ИНН не находится, а проверки уводят заявку в `need_info`.

## Запуск

Нужен Docker с compose v2. Больше ничего ставить не надо.

```sh
docker compose up -d --build --wait
```

| Что | Адрес |
|---|---|
| Фронт | http://localhost:8000 |
| API | http://localhost:8080/api, проверка: `/api/health` |
| Swagger UI | http://localhost:8082 |
| Temporal UI | http://localhost:8233 |
| Моки внешних систем | http://localhost:8081 |

Распознавание документов (Ollama, Qwen3-4B, Tesseract) в отдельном профиле, при первом запуске скачивается модель около 2,5 ГБ:

```sh
AI_ENABLED=true docker compose --profile ai up -d --build --wait
```

Значения по умолчанию лежат в `compose.yaml`, переопределяются через `.env` (образец в `.env.example`). Если порт занят, поменяй его там же.

## Вход

Сессии серверные: при входе `api` заводит сессию в Redis, в cookie `session` уходит подписанный токен с её номером. Выход удаляет сессию, токен сразу перестаёт работать. Попыток входа с одного адреса не больше `LOGIN_ATTEMPTS` за `LOGIN_WINDOW` (по умолчанию 10 в минуту). На стенде по http `COOKIE_SECURE=false`, за https его нужно включить, иначе cookie будет уходить открытым текстом.

## Заявки

Клиент создаёт черновик по ИНН (`POST /api/applications` с заголовком `Idempotency-Key`), правит его (`PATCH` с `version` из карточки) и может отменить до подачи. Повтор с тем же ключом отдаёт ту же заявку, тот же ключ с другим телом даёт 409 `idempotency_conflict`. Устаревшая `version` это 409 `version_conflict`, обнови карточку и повтори. Чужая заявка отвечает 404, как несуществующая. В ответе `allowed_next`: куда текущий пользователь может перевести заявку, по нему фронт рисует кнопки.

Подача `POST /api/applications/{id}/submit` сверяет анкету с условиями продукта из `rules/products.yaml` и требует оба согласия, `bki_consent` и `pd_consent` (ставятся в черновике, момент согласия пишется в базу). Что не так, приходит 422 `incomplete` со списком полей в `errors`. Дальше `draft -> submitted` и старт `ApplicationWorkflow` с id процесса, равным id заявки. Процесс стартует после коммита перехода, поэтому если Temporal не ответил, заявка остаётся в `submitted`, а клиент получает 503: повторная подача просто дозапускает процесс. Повтор по уже идущему процессу отвечает 200 с карточкой, второго workflow не появляется.

Допущения:

- компания, которой у нас ещё нет, заводится по выписке ЕГРЮЛ из мока, автор заявки становится её представителем в указанной роли; полномочия (руководитель из ЕГРЮЛ, доверенность для `proxy`) подача пока не сверяет: документов в заявке ещё нет, это появится вместе с загрузкой;
- к компании, у которой уже есть представитель, сам себя не добавишь: 403. Второго представителя на стенде заводит только сид;
- роль представителя одна на человека и компанию, правка роли в черновике меняет её и для других его заявок по этой компании;
- полноту анкеты и диапазоны продукта черновик не проверяет, только схема API: это делает подача;
- среднемесячную выручку подача не требует: нужна ли она, видно только по нашим оборотам, это решает шаг проверки;
- согласия пока флаги анкеты с моментом согласия, без версии текста и срока действия;
- после подачи отмена пойдёт через процесс заявки, сейчас отменить можно только черновик.

Очередь банка это тот же `GET /api/applications`: у `manager`, `underwriter` и `admin` в нём все поданные заявки, у клиента только его компаний, фильтры и сортировка общие. Черновик банку не виден ни в очереди, ни в карточке, ни в событиях: до подачи нет согласия на обработку данных, и делать с ним банку нечего. `sort=due_at` ставит сверху ближайший срок шага, `sort=score` самые рискованные, заявки без срока или без балла уходят в конец. В карточке сотрудник дополнительно видит `checks`, последний ответ каждого источника. Журнал `GET /api/applications/{id}/history` отдаёт переходы по порядку с автором и кодами причин; клиенту комментарии банка и системы не показываем, только его собственные. Разбивки скоринга, причин и рекомендации в карточке пока нет: их начнут писать скоринг и политика.

## Устройство

Модульный монолит: один репозиторий и один Go-модуль, но четыре процесса.

| Процесс | Что делает |
|---|---|
| `api` | HTTP API и живые события (SSE), стартует процесс заявки в Temporal |
| `worker` | ведёт заявку: проверки во внешних системах, скоринг, решение, выдача |
| `docs-worker` | распознаёт выписки и отчётность, отдельно, потому что тяжёлый и с другим образом |
| `mocks` | симулятор ЕГРЮЛ/ЕГРИП, ФНС, БКИ и внутренних данных банка |

Код разложен по слоям: `internal/domain` (сущности и правила без I/O), `internal/repo` (SQL через sqlc), `internal/usecase` (логика и транзакции), `internal/api` и `internal/worker` (вход снаружи). Переиспользуемая инфраструктура в `pkg/`. Контракт API в `api/openapi.yaml`, статусы заявки в `docs/state-diagram.md`, модель данных в `docs/data-model.md`.

Почему продукт устроен так, а не иначе: боли клиентов и банка, источники и границы MVP в [docs/research.md](docs/research.md).

## Разработка

Go 1.27, Node 24, Docker.

```sh
make generate   # сервер из api/openapi.yaml, код запросов из internal/db/queries
make lint
make test       # интеграционные тесты поднимают Postgres через testcontainers
make check      # всё, что проверяет CI
```

Фронт отдельно: `cd web && npm ci && npm run dev`, dev-сервер проксирует `/api` на `localhost:8080`.

## Синтетические документы

Для распознавания и кнопки «Взять пример выписки» лежит готовый набор в `testdata/documents`, пересобирается `make docgen`, повторный запуск даёт те же байты. Там выписки трёх форматов: a и b это текстовые PDF двух выдуманных банков с разными колонками и подписями, c это «скан» PNG с поворотом и шумом (один экземпляр завёрнут в PDF без текстового слоя). Плюс отчётность формата a и ловушка `0000300011_statement_a_trap.pdf`, где приход завышен в 1,5 раза. Рядом с каждым файлом `.truth.json` с полями, которые должно достать распознавание.

Компании: четыре демо и две из генератора (`0012345673`, `001234567887`). Один документ по любому ИНН:

```sh
go run ./cmd/docgen -inn 0000300011 -kind statement -format b -out /tmp/docs
```

Цифры считает `internal/mocks/synth`, тот же пакет будет кормить мок ФНС. Допущение: выручка за прошлый год в ФНС равна поступлениям по выписке за 12 месяцев (октябрь 2025 - сентябрь 2026). Иначе при росте выручки честная выписка расходилась бы с налоговой больше чем на 20% и падала в ручную проверку вместе с ловушкой.

## Документы заявки

Клиент грузит документ к черновику или по запросу банка (`need_info`): PDF, PNG или JPEG до 10 МБ, тип смотрим по содержимому, а не по расширению. Файл лежит в Postgres в `bytea`: файлы маленькие, бэкап и права те же, что у заявки, отдельное хранилище на демо не нужно. Выписка и отчётность с профилем `ai` уходят на распознавание, без него сразу `skipped`, остальные виды просто `uploaded`.

Итоги клиент подтверждает один раз (`POST /api/documents/{id}/confirm`), распознанные или введённые руками, разницы нет. Проверки те же, что после модели: не сошлось, 422 с ошибками по полям. Распознавание, которое дошло после подтверждения, его не перетирает. Смена статуса документа приходит в SSE событием `document`.

Пример выписки рисует `mocks`, nginx отдаёт ему `/api/samples/`, api про примеры не знает:

```sh
curl -o it.png 'http://localhost:8000/api/samples/0000300011?kind=statement&format=c'
```

## Распознавание документов

Работает только в профиле `ai`: `docs-worker` на очереди `docs` берёт текстовый слой PDF, сканы прогоняет через Tesseract (`-l rus+eng --psm 6`), поля по JSON-схеме достаёт `qwen3:4b-instruct-2507-q4_K_M` в Ollama, дальше проверки в Go: ИНН совпадает с заявкой, период до 13 месяцев и не в будущем, остаток на начало плюс приход минус расход равен остатку на конец, помесячный приход сходится с итогом. Не сошлось, документ `failed` и клиент вводит итоги руками. Без профиля документ `skipped`.

Настройки `docs-worker`: `TESSERACT_PATH` (по умолчанию `tesseract` из PATH), `TESSDATA_PREFIX`, если языки не в стандартном каталоге, `OLLAMA_URL`, `OLLAMA_MODEL`, `OCR_TIMEOUT` на страницу, `OLLAMA_TIMEOUT`.

Точность меряет `make eval-docs` на `testdata/documents`, итог с моделью, digest и временем в `docs/ai-eval.md`. Локально нужны tesseract с языками rus и eng и Ollama с моделью; ollama из compose порт наружу не публикует, так что для прогона подними свою или задай `OLLAMA_URL`.

Допущения: суммы в документе в рублях, отчётность в тысячах рублей пока не поддерживаем; не больше 5 страниц; модель видит первые 12 000 символов текста.

## Проверка интерфейса без бэкенда

В каталоге web: npm ci, npm run dev:mock. Обычный npm run dev отключает мок и проксирует /api на localhost:8080. Сессии и файлы мока сбрасываются при перезапуске. Расчёты предложений и подбор в моке демонстрационные.

npm run test:browser запускает изолированные сценарии на порту 5175. Нужен установленный Microsoft Edge; другой поддерживаемый канал задаётся BROWSER_CHANNEL (например chrome). Тесты не используют ваш браузерный профиль и не требуют бэкенда. Они проверяют вход, потерю сессии, анкеты, конфликт версий, документы, уточнения, предложения, коды и режим без мока. Отдельно перед PR: npm run lint и npm run build.

Работа по доверенности поддержана выбором роли и загрузкой документа. Браузерные проверки используют мок: совместимость фронтенда с актуальным серверным контрактом и полный процесс на настоящем API требуют отдельной интеграционной приёмки.
